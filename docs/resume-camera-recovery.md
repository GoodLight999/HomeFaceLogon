# スリープ復帰時のカメラ・認証処理の再開

## 報告と調査（2026-11-07）

スリープ復帰直後に「認識できませんでした」と表示され、カメラを起動せず
認証を終了することがある、という報告への修正です。v0.3.7 を含む main を基準にしています。
このPCはv0.3.7相当のカメラ高速化部品を導入済みですが、管理画面・アンインストール情報は
0.3.6 のままでした。版表示のみで認証部品の実装を判断していません。

確認できた欠陥は次の2点です。個々の過去の発生がすべて同じ経路かは未確定です。

- カメラ初期化・IPC待ちと異なり、顔認証ループの時間制限だけが `GetTickCount64` を使用し、
  スリープ時間も制限時間として消費していました。
- 選択されたCredentialがスリープ前から保持される場合に、復帰を契機として古いカメラ処理や
  失敗状態を破棄して再試行する処理がありませんでした。メッセージ専用ウィンドウは
  通常のブロードキャストを受けません。電源通知を明示購読した最初の候補も、実機では
  認証中のスリープ後に再開しませんでした。この候補は元の部品へ戻し、通知依存の実装を取り除きました。

## 修正

- 顔認証時間を `QueryUnbiasedInterruptTime` による稼働時間で計測します。
- Credentialのウィンドウで500msごとに、スリープ時間を含む時計と含まない時計の差を確認します。
  差が1秒以上増えた場合に復帰と判定し、CPU負荷やUI処理の遅延と区別します。
  時計の読み取りに100ms以上かかったサンプルは採用しません。
- 復帰を検出すると古いHostを停止し、認証結果と処理世代を破棄します。
  選択中の顔認証だけを新しいHostと新しい認証時間で再開します。
- タイマーより先に古いHostの結果が届く場合も、受理前に時計を確認します。
  資格情報のシリアライズ前にも確認し、古い結果で自動ログオンしません。
- 選択解除・イベント購読の交換・Providerからの切り離しで、保留中の再開を取り消します。
  時計の履歴は購読の交換を挟んでも保持し、古い顔認証結果を再利用しません。

PINの試行回数制限と顔認証成功の有効期限は変更していません。

## 検証

- C++ Release x64 ビルド成功。
- Credential回帰テスト15グループ成功。17時間のスリープに相当する時計の差を注入し、
  スリープで認証時間を使い切らず、実際の稼働時間では正常に期限切れになることを確認。
- 電源通知を一切送らず、時計差だけで古い顔認証結果を破棄して再開することを検証。
  認証終了後の復帰、選択解除、タイマーより先の結果配送・シリアライズ、購読交換を含みます。
- スリープ時間を含む時計へ戻した場合と、復帰検出を無効にした場合は、追加テストが
  対応する不具合で失敗することを確認。実際のスリープを行った検証とは区別しています。
- 実際のHost・カメラ・登録済みモデルを使うパイプ通しテストで、約2.4秒で最初の映像と
  STATUSを受信。Windowsへの資格情報の送信は行いません。

最終方式を実機へ反映した後、カメラを覆って起動してからスリープし、30秒以上待って復帰、
覆いを外して顔認証で解除できたことをユーザーが確認しました。
15:50:18の実ログで時計差による復帰検出と新しいHostの起動を確認し、
15:50:24に顔一致、資格情報の生成、`ReportResult(STATUS_SUCCESS)` を確認しました。
実機確認の対象は、このPCで今回行った復帰操作です。
試験反映はHostとProviderの2ファイルに限定し、管理アプリ、登録データ、ネットワーク設定は変更しません。
登録データ4ファイルとEnabledの保持、COM生成、候補とインストール済み部品の一致を確認済みです。

GitHubのPRは #3。CIはアカウントの請求上の問題によりジョブ開始前に停止しています。
コードのビルド・テスト失敗とは区別します。上記のローカル検証は成功しています。
